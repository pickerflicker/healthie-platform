# Optional provider credentials as an array

Accepted 2026-10-20 for PIC-285. Store the small fixed set of professional abbreviations on Provider as a non-null PostgreSQL string array with an empty default. Validate supported values and normalize at the profile boundary. Per Steven’s 2026-10-21 PR feedback, application validation is sufficient for these display choices; remove the earlier allowed-set CHECK and squash the two unmerged migrations into one add-column migration. Use the supported-list order for storage/display and treat the checkbox empty sentinel as clearing, with duplicate selections removed. Assume well-formed arrays of strings and reject unsupported codes rather than silently storing them. An empty array clears the selections.

This keeps an optional display field small and explainable, without a join table or generic credentialing subsystem. The tradeoff is PostgreSQL-specific array storage and reliance on application validation for the catalog; direct SQL can bypass that validation. Catalog updates require only a code change. A separate model would become appropriate if credentials later need jurisdiction, expiry, license numbers or verification; none is currently authorized.

The provider edits its own credentials through Devise/Pundit and a server-derived profile. Names remain User identity data. Credentials never grant permissions or affect enrollment plans. Scalar client-list rows include the array through joins/pluck; a new cache-key version bypasses legacy payloads, and committed changes invalidate every enrolled client's list.

Expanded 2026-10-20 to 50 curated U.S.-focused choices grouped in the editor. Exact mixed-case/hyphenated codes remain display selections, with no role equivalence or automatic selection. The unmerged credential migrations were subsequently squashed into one add-column migration per review. The laptop’s already-applied schemas were reconciled by removing the credential CHECK and obsolete expansion migration receipt, retaining the column and saved selections. Fresh installs use the single migration; rolling it back removes the column and its data.
